## 1. 何を作るのか

HTMLで作ったゲームやプロダクトを、**投稿はログイン必須・閲覧とプレイと評価とコメントは誰でも自由**で扱うプラットフォーム。サービス名は **frank pro**。

狙いは「ゲームを効率よく消費できる」こと。作品を売る場所ではなく、次々と触っていける場所。

UIはYouTubeや海外のPC無料ゲームサイトのようなグリッド一覧型。アイコン＋短い説明が並び、押すとその場で遊べる。スワイプフィード型は却下（外れを引いたときのストレスが大きい）。

**市場の空白**

- Poki、CrazyGames → 審査を通った作品だけ。個人が即投稿できない
- itch.io → 誰でも投稿できるが、ストアのページ構造で遊ぶまでが遠い

「誰でも即投稿 × 一覧からワンタップで即プレイ」を両立している場所がない。ここを狙う。

## 2. 運営ポリシー（最重要・v2で確定）

> **セキュリティ上の不正は全力で防ぐ。それ以外の不正は許容する。**

「それ以外の不正」とは、票の水増し、自作自演、コメントスパムなど。
検知・排除の仕組みは作らない。実装が重くなる上に、攻撃側が常に一手先を行く勝負になるため。

この方針の対象外が2つある。どちらも「不正」ではなく別の問題なので、削らない。

1. **権利侵害と誹謗中傷への対応**（通報・非表示・削除）— 法的リスク
2. **投稿HTMLの隔離**（CSP・sandbox）— セキュリティそのもの

## 3. 確定している仕様

| 項目 | 決定 |
|---|---|
| 投稿 | ログイン必須 |
| 閲覧・プレイ | ログイン不要 |
| 星評価 | **ログイン不要。全票同一重み（w=1.0）** |
| コメント | **ログイン不要。事前審査なし、投稿即公開** |
| 作品の形式 | HTML1ファイル完結。外部通信なし |
| 一覧の並べ替え | アクセス数 / 評価数 / 評価率 / 新規 の4種 |
| アクセス数 | 同一 visitor_id につき1日1カウント |
| 評価率 | ベイズ平均。m は日次バッチで票数中央値に追従 |
| ファイルサイズ上限 | 10MB |
| UI方針 | AppleのHuman Interface Guidelinesに沿ったApple風 |
| 初期コンテンツ | 0本で開始 |
| サービス名 | **frank pro** |

**後からまとめて全部入れる（雑に削らない）**：作者ページ（作品一覧＋SNSリンク）、星評価、評価コメント欄。

作品内スコアランキング（ゲームごとの順位表）は不要と判断済み。postMessageでスコアを親に渡す設計は破棄。

## 4. 評価率の計算

星5段階で「遊ばずに付けてOK」にすると、1票だけ5点の作品が満点で首位に来て、票が集まった良い作品が沈む。票の重み付けをしない以上、**これへの防御はベイズ平均1本だけ**になる。必ず最初から入れる。

```
スコア = (v / (v + m)) × R + (m / (v + m)) × C

R = その作品の平均点
v = その作品の票数
m = 基準票数 … 全作品の票数の中央値（最低3、上限20でクランプ）を日次更新
C = サイト全体の平均点（実測をそのまま使う）
```

票が少ないと C に引っ張られ、票が増えるほど R に近づく。
式ひとつなので**最初から入れる**。後から入れると並び順が大きく動いて混乱する。

星評価は甘く出るので C は 4.2 前後に落ち着く見込み。新作は中位スタートになる。これは健全なので調整しない。

## 5. 発見の仕組み（0本スタート対策）

機械的な人気順は、作品が少ないうちは何も並ばない。3つ用意する。

1. **「今週の frank」枠** — 運営が手で押し出す。ただし恒久的な特等席にはしない。
   毎週入れ替わる前提にしておかないと「なぜ選ばれないのか」の説明責任が発生する。
   データは `featured(work_id, start_at, end_at, slot)`。後で自動選出に差し替えられる形にしておく。
2. **「適当に遊ぶ」ボタン（ランダム1本）** — 初期の最大の発見装置。
   人気順が固定化した後もロングテールに触らせる唯一の手段。狙いの「効率よく消費」に一番近い機能。
3. **既プレイ作品のマーク** — localStorage で十分（親ページは同一オリジンなので使える）。
   ログイン不要のまま実現できる。効率よく消費するには「もう触ったやつを避ける」が要る。

あわせて、**閉じたときのスクロール位置保持**と、**作品ごとのURL**（`history.pushState` でモーダル、戻るボタンで一覧に復帰）。ここができていないサイトは全部ストレスになる。

## 6. 技術構成（サーバー代ゼロ前提）

| 役割 | 使うもの | 理由 |
|---|---|---|
| HTMLの置き場・配信 | Supabase Storage | 無料枠にカード登録不要・超過時も自動課金されない（当初R2予定だったが変更。security-design.md 1-1-補） |
| 配信ヘッダの強制 | Cloudflare Workers | ストレージの前に1枚挟む。ヘッダ付け忘れが致命傷になるため。エッジキャッシュで帯域も節約 |
| DB・認証・一覧データ | Supabase 無料枠 | Postgres＋Authが揃う |
| サイト本体 | Cloudflare Pages | 静的配信で実質無料 |
| サムネ生成・日次バッチ | GitHub Actions ＋ Playwright | 常時ヘッドレスを動かすと無料枠を超える。1日1回まとめて未処理分だけ撮る |

容量は問題にならない（HTML1本は数十〜数百KB、1000本で100MB程度）。転送量はCloudflare Workerの
エッジキャッシュ（1時間TTL）で大部分を吸収し、Supabase Storage側の無料枠（月間帯域5GB）を節約する。

**各社の無料枠の数字は変わるので、着手前に現在のページで確認する。**

日次バッチでやること（1ジョブにまとめる）：
- 未処理作品のサムネ撮影
- ベイズ平均の `m` と `C` の再計算
- 6ヶ月を過ぎたコメントログの削除

### サムネは3段構え

日次バッチだけだと投稿から最大24時間サムネなし。「新規順」の先頭が灰色の箱になるのは新規投稿者の体験として最悪。

1. 投稿時に作者が**任意でアップロード**（見せたい画面を選べる）
2. 無ければ**タイトル＋自動生成カラーのプレースホルダ**（窓の見た目なら様になる）
3. 日次バッチが撮って置き換え

## 7. セキュリティ

**詳細は `security-design.md` を参照。実装時は必ずそちらを開くこと。** ここは要約のみ。

### 方針

コードを読んで `fetch` や `eval` を検出する方式は採用しない。文字列を分割して組み立てられたら検出できず、攻撃側が常に勝つ。代わりに**実行環境側で塞ぐ**。判定を自分でやらないので抜け道探しの勝負にならない。

副作用として外部の画像・フォント・音源も読めなくなり、自動的に「1ファイル完結」が強制される。企画の縛りと防御策が一致している。

### 最重要の2点

1. **`Content-Security-Policy: sandbox allow-scripts` をレスポンスヘッダで付ける。**
   iframeの `sandbox` 属性だけでは、Supabase Storageの公開URLを直接開かれたときに効かない。
   そのとき作品は配信ドメインの正規オリジンとして動き、他作品のストレージが読め、
   そのドメイン上でフィッシングページとして成立してしまう。
   （Google「Securely hosting user data in modern web applications」の推奨）

2. **`allow-same-origin` は絶対に付けない。**
   付けると投稿者のJSがこちらのCookieやDOMに触れる。
   副作用として作品は localStorage に触れなくなり、触ると SecurityError で停止する。
   → 投稿ガイドラインに明記済み。「投稿したのに真っ白」の最多原因になる見込み。

### 残存リスク（認識した上で受け入れる）

- **WebRTC は `connect-src` の管轄外。** `webrtc 'block'` はChromium系のみ、Firefox未実装。
  ただし opaque origin なので盗めるデータがそもそもほぼない
- **CPU消費は止められない。** 無限ループ、マイニング。サーバー負荷にはならないが端末が焼ける
- `'unsafe-inline'` / `'unsafe-eval'` を許す以上、任意のJSが動く。封じているのは外に出す経路だけ

## 8. 規約・運用

`terms-of-service-draft.md` と `posting-guideline-draft.md` に叩き台がある。
**土台を組む前にサイトに置く。** 後回しにすると作り直しになる種類。

要点：

- 投稿物の権利は投稿者のまま。サイトは表示のための非独占的利用許諾を受けるだけ
- 通報の受付窓口を置く（規模に関わらず実務上必須）
- **作者が自分の作品のコメントを非表示にできる** — 運営コストを分散する最重要の仕組み
- **コメントのIPとUAを6ヶ月保存し、規約に明記する。**
  匿名コメントを許す＝発信者情報開示請求の窓口になる。
  記録がないと開示に応じられず、運営者として苦しい立場になる
- 情プラ法の重い義務は「大規模特定電気通信役務提供者」として指定された事業者が対象。個人の規模は対象外

※ 法律の専門家ではない人間が作った叩き台。人を集める段階なら十分だが、
**収益化・法人化・広告のいずれかを踏む段階で専門家に見てもらう。**

## 9. 開発の進め方（GitHub を使う）

結論：**GitHub リポジトリを作って、そこで進める。** 理由は3つ。

1. **Cloudflare Pages は GitHub リポジトリを見て自動デプロイする。**
   push するだけで本番が更新される。手動アップロードは続かない
2. **サムネ生成の GitHub Actions は、リポジトリがないと動かない。**
   これは既に技術構成で決めていること
3. **壊したときに戻せる。** 一番効くのはこれ

リポジトリは **public** にする。GitHub Actions の実行時間が public リポジトリなら無料だから。
APIキーやトークンはコードに書かず、**GitHub Secrets と Cloudflare/Supabase の環境変数**に入れる。
ここさえ守れば public で問題ない。

### 着手前に用意するもの（人間がやる作業）

```
□ GitHub アカウント → リポジトリ frank-pro を public で作成
□ Cloudflare アカウント（Workers / Pages は無料枠にカード登録不要）
□ Supabase アカウント → プロジェクト作成、リージョンは Tokyo
□ ドメイン取得（frank.pro が取れるか確認する。.pro は実在のTLD）
□ PC上に作業フォルダを作り、git clone する
□ Cowork の「フォルダを追加」でそのフォルダを接続する
```

最後の1つが要。フォルダを接続すると、Claudeがそのフォルダの中で直接ファイルを読み書きできる。
接続していないと、毎回ファイルを手で受け渡すことになって進まない。

### 想定するフォルダ構成

```
frank-pro/
├─ web/              … Cloudflare Pages にデプロイする静的サイト
├─ worker/           … Supabase Storage の前に置く Cloudflare Worker（配信ヘッダの強制）
├─ supabase/
│   ├─ migrations/   … テーブル定義と RLS
│   └─ functions/    … Edge Function（署名URL発行、評価・コメントの受け口）
├─ .github/workflows/
│   └─ daily.yml     … サムネ生成＋m,C再計算＋古いログ削除
└─ docs/             … この引き継ぎまとめと3つの設計文書
```

### 実装の順序

1. リポジトリ作成、Cloudflare Pages と接続（空のページが公開されるところまで）
2. Supabase のテーブルと RLS
3. Worker ＋ Supabase Storage の配信経路。**先に security-design.md のヘッダを通して、
   手で置いたテストHTMLが opaque origin になることを確認する**
4. 投稿フロー（Edge Function 経由の署名URL、縦長プレビュー、サムネ任意アップロード）
5. 一覧（4種の並べ替え）と作品ページ
6. 日次バッチ
7. 作者ページ、星評価、コメント欄
8. 規約・ガイドラインのページ

3 を 4 より先にやること。配信の隔離が効いていない状態で投稿を受け付けると、
後から直すときに既存作品の扱いで詰まる。

## 11. すでに作ってあるもの

**`mado.html`** — グリッド一覧＋即プレイのデモ。単体HTMLで、実際に遊べる7本入り。

- タイルを小さなブラウザ窓の見た目にしてある
- 開くと全画面でプレイ、閉じると iframe を破棄
- `sandbox="allow-scripts"` のみ、`allow-same-origin` なし
- 投稿ボタンはログインの壁で止まる

このデモの見た目は意図的にApple風から外してある（HIG方針を決める前に作ったもの）。
**本番のUIは作り直す前提。** 動きと構造の確認用として見る。
